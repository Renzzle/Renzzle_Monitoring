# 대시보드·지표 가이드

Grafana 대시보드 5개의 구성과 지표 정의, 이상 징후를 판단하는 기준을 정리한다. 패널마다 한 줄 설명이 제목 옆 ⓘ에 있고, 이 문서는 그보다 자세한 내용을 다룬다.

## 대시보드 구성

| 대시보드 | 용도 | 데이터 |
|---|---|---|
| 서비스 현황 | 활성 사용자, 가입, 기능 사용, 게임 지표. Grafana 홈 화면 | Loki |
| 결제 | 인앱결제, 환불, 결제 실패, 재화 흐름 | Loki |
| 유저 추적 | 유저 한 명의 요청, 결제, 오류 로그 | Loki |
| 장기 추이 | 월별 MAU, 일별 DAU, 월별 가입·결제 등 장기 추이 | prometheus-kpi |
| 서버 상태 | HTTP 요청, JVM, DB 커넥션 풀, 시스템 자원 | Prometheus, Loki |

서비스 지표는 앱 로그로, 서버 지표는 메트릭으로 계산한다.

- 로그: 요청마다 남는 접근 로그와 결제·랭크 같은 이벤트 로그다. 유저 ID가 있어 유저 단위로 볼 수 있다.
- 메트릭: Spring Boot(Micrometer)가 15초마다 내보내는 수치다. 유저 정보는 없다.
- 집계 지표: 로그에서 일·주·월 단위로 계산한 숫자다. 유저 ID 없이 숫자만 남는다.

로그와 메트릭은 90일, 집계 지표는 기간 제한 없이 보관한다.

모든 대시보드에 공통으로 적용되는 규칙은 다음과 같다.

- 시간은 한국시간(KST) 기준이다.
- 제목에 `(선택 기간)`이 붙은 패널은 오른쪽 위 시간 범위를 따른다. `(최근 30일)`처럼 기간이 적힌 패널은 시간 범위와 상관없이 그 기간을 보여 준다.
- 표의 유저 ID를 누르면 유저 추적 대시보드로 이동한다.

## 서비스 지표

| 지표 | 정의 |
|---|---|
| DAU / WAU / MAU | 로그인한 상태로 API를 한 번 이상 호출한 유저 수. 기간 안에서 같은 유저는 한 번만 센다 |
| 일·주·월 | 일은 KST 0시, 주는 월요일, 월은 1일에 시작한다 |
| 고착도 | 최근 24시간 활성 유저 ÷ 최근 30일 활성 유저. 20% 이상이면 양호한 편이다 |
| 신규 가입 / 탈퇴 | 회원가입 API와 회원 탈퇴 API의 성공(200) 건수 |
| 기능별 사용량 | API(메서드 + 경로)별 호출 수와 사용자 수. 실패한 호출도 포함한다 |
| 결제 건수 | 영수증 검증과 재화 지급까지 끝난 인앱결제 건수 |
| 결제 전환율 | 결제 유저 ÷ 같은 기간 활성 유저 |
| 랭크 정답률 | 랭크에서 출제된 문제 중 정답 비율. 서버가 검증하지 않고 클라이언트가 보고한 결과를 센다 |

다음은 집계에 들어가지 않거나 따로 찾아야 하는 항목이다.

- 로그인 전 요청(회원가입, 로그인, 토큰 재발급 등)과 웹 공유 페이지 조회는 활성 유저에 포함되지 않는다. 공유 페이지 조회는 서비스 현황에서 따로 센다.
- 로그에는 숫자 유저 ID만 남는다. 닉네임으로 찾을 때는 어드민 페이지나 DB에서 ID를 먼저 확인한다.
- 환불 로그는 스토어 알림과 정기 작업에서 기록되므로 유저 ID가 없다. 결제 ID로 원래 결제를 찾는다.
- 로그에 가격이 없어 매출액은 집계하지 않는다.

## 장기 추이

로그는 90일이 지나면 지워지므로, 오래 볼 지표는 Loki가 미리 계산해 `prometheus-kpi`에 쌓는다. 계산 규칙은 `loki/rules/fake/kpi.yml`에 있고, 서비스 현황 대시보드와 같은 정의를 쓴다.

| 지표 | 단위 | 계산 주기 |
|---|---|---|
| 활성 유저 (DAU, WAU, MAU) | 일, 주, 월 | 일 1시간, 주·월 12시간 |
| 신규 가입, 탈퇴 | 일 | 1시간 |
| 결제 건수 (상품·플랫폼별) | 일 | 1시간 |
| 결제 유저 수 | 월 | 12시간 |
| 환불 건수, 랭크 게임 수 | 일 | 1시간 |
| 영역별 API 호출 수 | 일 | 1시간 |

월 합계(월별 가입, 월별 결제 건수 등)는 일 단위 값을 더해서 보여 준다. 활성 유저는 중복을 빼야 하므로 주·월 단위를 따로 계산한다.

읽을 때 알아둘 점은 다음과 같다.

- 배포한 날부터 쌓인다. 그 전 기간은 비어 있다.
- 오늘, 이번 주, 이번 달 값은 집계 중이라 기간이 끝날 때까지 계속 오른다.
- 기간이 끝난 뒤에도 일은 12시간, 주는 2일, 월은 3일 동안 다시 계산한다. 그 안에 서버가 잠시 멈췄다 돌아와도 값이 빠지지 않는다. 그보다 오래 멈추면 해당 기간 값이 일부만 남을 수 있다.
- 새 지표를 추가하면 그날부터 쌓인다. 규칙 파일에 기록 규칙을 추가하고 `docker compose restart loki`로 반영한다.

## 서버 지표

서버 상태 대시보드는 Google SRE의 네 가지 골든 시그널(트래픽, 오류, 지연, 포화)을 기준으로 구성했다. 맨 위 상태 요약에서 이상 여부를 먼저 판단하고, 원인은 아래 섹션에서 찾는다.

| 시그널 | 상태 요약 패널 | 원인을 볼 섹션 |
|---|---|---|
| 트래픽 | 처리량 (RPS) | HTTP 요청 |
| 오류 | 5xx 에러율 | HTTP 요청, 로그 |
| 지연 | 평균 응답 시간 | HTTP 요청, DB 커넥션 풀 |
| 포화 | 힙 사용률 | JVM, DB 커넥션 풀, 시스템 자원 |

아래 표의 정상 범위는 지금 서비스 규모에서 출발점으로 잡은 값이다. 운영하면서 평소 수치를 보고 조정한다.

### HTTP 요청

| 지표 | 의미 | 정상 범위 | 이상 징후 |
|---|---|---|---|
| 처리량 (RPS) | 초당 처리한 요청 수 (actuator 제외) | 사용 패턴에 따라 변동 | 갑자기 0이면 앱 다운이나 앞단(Cloudflare, Caddy) 장애 |
| 4xx | 클라이언트 요청 문제로 거절한 응답. 401 토큰 만료, 400 잘못된 요청, 409 중복 등 | 소량 | 특정 API에서 급증하면 앱 배포 후 요청 형식이 바뀌었는지 확인 |
| 5xx | 서버가 요청 처리에 실패한 응답. 버그, DB 장애 등 | 0 | 로그 섹션의 에러 코드 분포와 ERROR 로그 확인 |
| 평균 응답 시간 | 전체 요청의 평균 | 수십 ms | 300ms 이상이 계속되면 지연 |
| p95 응답 시간 | 요청의 95%가 이 시간 안에 끝난다 | 평균의 몇 배 이내 | 평균은 그대로인데 p95만 오르면 일부 API가 느린 것. 지연 상위 API 확인 |
| 최대 응답 시간 | 가장 느린 요청 하나 | 가끔 튄다 | 높은 값이 계속되면 확인 |

p95는 앱 서버에 `slo` 설정([README](../README.md#앱-서버-설정-renzzle_be))이 배포된 뒤부터 표시된다.

### JVM

| 지표 | 의미 | 정상 범위 | 이상 징후 |
|---|---|---|---|
| 힙 메모리 | 자바 객체가 쓰는 메모리. Used(사용 중), Committed(OS에서 확보), Max(상한) | GC 때문에 톱니 모양으로 오르내린다 | 톱니의 저점이 계속 오르면 메모리 누수 의심 |
| GC 후 힙 사용률 | GC 직후에도 남은 장수 객체 비율. 앱이 실제로 붙잡고 있는 메모리다 | 일정 수준 유지 | 며칠에 걸쳐 오르면 누수, 80% 이상이면 힙 증설 검토 |
| GC 정지 시간 | GC 동안 애플리케이션이 멈춘 시간. 정지 비율과 최대 정지 시간을 본다 | 비율 1% 미만, 최대 수십 ms | 최대 수백 ms면 그 시점의 요청이 지연된다 |
| Non-Heap 메모리 | Metaspace(클래스 정보), CodeCache(JIT 컴파일 코드) 등 | 기동 후 몇 분 안에 안정 | 계속 오르면 클래스 누수 (드물다) |
| 스레드 상태 | 상태별 스레드 수 | 요청량에 따라 증감 | BLOCKED가 계속 보이면 락 경합, 전체 수가 계속 늘면 스레드 누수 |

### DB 커넥션 풀 (HikariCP)

HikariCP는 MySQL 커넥션을 미리 열어 두고 재사용한다. 풀 크기는 기본 10이다.

| 지표 | 의미 | 정상 범위 | 이상 징후 |
|---|---|---|---|
| Active / Idle | 사용 중인 커넥션과 쉬고 있는 커넥션 | Active가 Max보다 충분히 낮음 | Active가 Max에 붙어 있으면 느린 쿼리가 커넥션을 오래 잡고 있는 것 |
| Pending | 커넥션을 기다리는 요청 수 | 0 | 1 이상이면 요청이 커넥션을 기다리느라 지연된다 |
| 커넥션 획득 시간 | 풀에서 커넥션을 받기까지 걸린 시간 | 1ms 미만 | 늘어나면 풀이 부족한 것 |
| 커넥션 타임아웃 | 30초 안에 커넥션을 받지 못해 실패한 요청 수 | 0 | 1 이상이면 그 시점에 DB 지연이나 풀 고갈이 있었다 |

### 시스템 자원

| 지표 | 의미 | 정상 범위 | 이상 징후 |
|---|---|---|---|
| CPU 사용률 | Process는 앱, System은 서버 전체의 사용률 | 요청량에 따라 변동 | 80% 이상이 계속되면 자원 부족 |
| Load Average (코어당) | 1분 평균 실행 대기 작업 수 ÷ 코어 수 | 1 미만 | 1 이상이 계속되면 CPU 포화 |
| 파일 디스크립터 | 앱이 열어 둔 파일과 소켓 수 | 일정 범위에서 변동 | 계속 늘기만 하면 커넥션이나 파일을 닫지 않는 버그 |
| 디스크 여유 공간 | 앱 서버 디스크의 여유 비율 | 20% 이상 | 10% 미만이면 로그와 DB 쓰기 실패 위험 |

## 증상별 확인 순서

### 앱이 동작하지 않는다는 문의

1. 서버 상태의 수집 상태가 `중단`이면 앱 서버와 Alloy부터 확인한다.
2. 업타임이 짧으면 최근에 재시작됐는지 본다. 그래프의 보라색 세로선이 재시작 시점이다.
3. 5xx 에러율이 올랐으면 에러 코드 분포와 최근 ERROR 로그에서 원인을 찾는다.

### 응답이 느리다

1. 응답 시간 패널에서 평균과 p95 중 무엇이 올랐는지 본다.
2. 지연 상위 API에서 느려진 API를 찾는다.
3. 커넥션 풀 상태의 Pending과 커넥션 획득 시간으로 DB 대기를 확인한다.
4. GC 정지 시간과 CPU 사용률을 확인한다.

### 특정 유저의 문의

1. 유저 추적에 유저 ID를 입력한다.
2. 오류 응답 수와 WARN·ERROR 로그에서 문제가 생긴 시점을 찾는다.
3. 최근 요청 표에서 해당 요청의 traceId를 누르면 그 요청에서 나온 로그만 모아서 볼 수 있다.

### 결제 문의

1. 결제 대시보드의 결제 실패 원인에서 에러 코드를 확인한다. I4090(중복 영수증)과 I4091(결제 보류)은 앱이 재시도하는 과정에서 흔히 생긴다.
2. 유저 추적의 결제 로그에서 해당 유저의 검증·지급 기록을 본다.
3. 환불 건은 결제 대시보드의 환불·스토어 알림 로그에서 결제 ID로 찾는다.

## 기존 템플릿 대시보드

예전에 grafana.com에서 가져온 대시보드 3개는 Grafana에 그대로 남아 있다. 지표는 서버 상태 대시보드와 같고, 섹션별 대응은 다음과 같다. 섹션 이름은 템플릿 버전에 따라 조금 다를 수 있다.

JVM (Micrometer)

| 섹션 | 내용 | 서버 상태 대시보드 |
|---|---|---|
| Quick Facts | 가동 시간, 힙·Non-Heap 사용률 | 상태 요약 |
| I/O Overview | 요청 수, 에러, 응답 시간 | HTTP 요청 |
| JVM Memory, Memory Pools | 힙·Non-Heap, 영역별(Eden, Old Gen, Metaspace 등) 메모리 | JVM |
| JVM Misc | CPU, load, 스레드, 파일 디스크립터 | JVM, 시스템 자원 |
| Garbage Collection | GC 횟수와 시간, 메모리 할당·승격 속도 | JVM |
| Classloading, Buffer Pools | 로드된 클래스 수, NIO 버퍼 | 없음. 특정 문제를 추적할 때만 본다 |

Spring Boot 2.1 System Monitor

| 섹션 | 내용 | 서버 상태 대시보드 |
|---|---|---|
| Basic Statistics | 가동 시간, 힙·CPU 사용률 | 상태 요약 |
| JVM Statistics | 메모리, GC, 스레드 | JVM |
| HikariCP Statistics | DB 커넥션 풀 | DB 커넥션 풀 |
| HTTP Statistics | 요청 수, 응답 시간 | HTTP 요청 |
| Tomcat Statistics | 세션, 스레드. 이 앱은 세션을 쓰지 않아 대부분 비어 있다 | 없음 |
| Logback Statistics | 레벨별 로그 수 | 로그 |

Spring Boot - Logs (Loki)는 로그를 레벨별로 보는 대시보드로, 서버 상태의 로그 섹션과 유저 추적의 이벤트 로그가 같은 역할을 한다.

새 대시보드로 충분하면 세 대시보드는 지워도 된다. 대시보드를 지워도 수집된 데이터는 남는다.

## 대시보드 수정

Grafana는 시작할 때 `grafana/dashboards/`의 JSON 파일로 대시보드를 만든다. 화면에서 고친 내용은 저장되지 않고, 재시작하면 파일 내용으로 돌아간다.

임시로 바꿔 볼 때는 복사본을 만든다. Edit을 누르고 Save 옆 화살표에서 Save as copy를 고른다. 복사본은 Grafana 안에만 저장된다.

바꾼 내용을 레포에 반영하는 순서는 다음과 같다.

1. 화면에서 대시보드를 고친다. 저장은 하지 않아도 된다.
2. 오른쪽 세로 툴바의 Export 아이콘에서 Export as code를 고른다.
3. Advanced options를 펴고 Model은 Classic, Format은 JSON을 고른다. 기본값인 V2 Resource로 내려받으면 지금 파일과 형식이 달라 프로비저닝에 쓸 수 없다.
4. Share dashboard with another instance는 끈 채로 Download file을 누른다.
5. 내려받은 파일로 `grafana/dashboards/`의 같은 이름 파일을 교체하고 커밋한다.
6. 서버에서 `git pull`을 하면 1분 안에 반영된다.

BE에 API가 추가되면 기능별 사용량 표에는 `POST /api/...` 같은 경로가 그대로 표시된다. 이름을 붙이려면 서비스 현황과 유저 추적 대시보드의 기능별 사용량 표에서 Value mappings에 경로와 이름을 추가한다.
